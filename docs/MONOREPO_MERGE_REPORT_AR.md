# تقرير دمج TRINEX-main في TRINEX Platform

**التاريخ:** 29 أكتوبر 2026  
**النطاق:** تطبيق الإدارة، تطبيق الطلاب، والـBackend ضمن Monorepo.  
**مهم:** هذا الدمج انتقائي، ولم يتم استبدال المشروع الحالي بالنسخة القديمة.

## 1. ما تم أخذه من TRINEX-main وما تم تغييره

- استعادة واجهة صندوق البلاغات والمقترحات القديمة، مع توصيلها بعقد API وجداول جديدة للبلاغات العامة والمقترحات وبلاغات الرسائل المبلّغ عنها. أضيف مسار API لحفظ بلاغ الرسالة، لكن لا توجد شاشة دردشة حالية يمكن إضافة زر الإبلاغ إليها.
- الاستفادة من تجربة تفاصيل البلاغ وتغيير الحالة وإضافة الملاحظات الإدارية.
- الاستفادة من صفحة التحليلات القديمة بوصفها مرجعًا، ثم إنشاء صفحة تشغيلية مختلفة عن النظرة العامة، مع مسار `/admin/analytics/overview`.
- الاستفادة من تجربة إدارة السوق الموجودة وإخراجها من الإدارة الإضافية إلى مدخل مستقل باسم «السوق».
- إزالة إدارة الشارات من لوحة الإدارة، وجعل تعريفاتها ثابتة ضمن إصدار الـBackend. بقيت الجداول والترحيلات التاريخية لتجنب كسر قواعد بيانات موجودة.
- إزالة صفحة إشراف التعليقات الإدارية، وإعادة صلاحية «الطالب المشرف» من خلال تعيينها في صفحة الطلاب، وإضافة تفويض الحذف على الخادم للتعليقات والردود مع تسجيل عمليات الإشراف في سجل التدقيق.
- فصل الجداول الدراسية عن المواد في التنقل، ونقل الوصول إلى إدارة الامتحانات إلى بنر في صفحة المواد الدراسية. لم تعد الامتحانات مدخلًا مستقلًا في القائمة الجانبية، ولم تعد ضمن الإدارة الإضافية.
- إضافة تحديد جماعي بالسحب/الضغط المطول أو من قائمة السجل، وتحديد الكل، وإلغاء التحديد، والحذف الجماعي في صفحات المحتوى والمواد والجداول والطلاب والسوق. بقيت قوائم إجراءات السجل الفردي.
- إضافة نموذج في تطبيق الطلاب لإرسال المقترحات والبلاغات العامة.
- نقل ملفات التوثيق الخمسة عشر الخاصة بالنسخة القديمة إلى `docs/legacy/TRINEX-main/` للاحتفاظ بها كمرجع تاريخي، لا كتوثيق حالي لعقد الـAPI.

## 2. حدود معروفة في التنفيذ

- **بلاغات الدردشة:** لا توجد في الـMonorepo الحالي منظومة رسائل دردشة حيّة أو جدول رسائل أو شاشة دردشة يمكن إضافة زر الإبلاغ إليها. أضيف مسار API يستقبل بلاغًا مع نسخة من الرسالة، ويمكن للإدارة معالجة سجل البلاغ، لكن تجربة الإبلاغ من واجهة الطالب غير موصولة لعدم وجود شاشة مصدر، وتغيير حالة «الرسالة» يحدّث قرار البلاغ/النسخة المحفوظة فقط ولا يحذف رسالة حيّة. يلزم تنفيذ نظام الرسائل نفسه قبل إكمال الإبلاغ والإشراف عليها من طرف المستخدم.
- **استهلاك Cloudflare الفعلي:** صفحة مراقبة النظام تعرض إحصاءات قاعدة البيانات، سجل التدقيق، أحداث الدخول ومزامنة Drive. لا تعرض استهلاك Worker CPU أو إجمالي طلبات الحساب والفوترة؛ هذه البيانات تحتاج ربطًا رسميًا بواجهة Cloudflare Analytics أو Analytics Engine، وهو غير مهيأ في الأرشيف الحالي. زمن فحص D1 لا يعادل استهلاك CPU أو الفوترة.
- **الماسح الضوئي:** لم تُعد واجهة الاستيراد القديمة إلى التطبيق؛ لأن `/admin/imports`, `/admin/imports/:id` و`/admin/imports/ocr` ومخزن عمليات الاستيراد غير موجودة في الـBackend الحالي. إعادة الواجهة وحدها تعيد أزرارًا لا تعمل. يجب تنفيذ مسار الاستيراد كاملًا (بما في ذلك OCR، المراجعة، الاعتماد، وتاريخ العملية) قبل إعادتها. عند ذلك يجب الالتزام بمزود OCR المتفق عليه وعدم إعادة مسار Eino Vision الاحتياطي القديم تلقائيًا.

## 4. اختلافات Monorepo الجديدة التي تم الإبقاء عليها

هذه الوظائف ليست جزءًا من أرشيف تطبيق الإدارة القديم، ولذلك لم تُستبدل أو تُحذف عند الاستفادة من `TRINEX-main`:

- تطبيق الطلاب المستقل ومكوناته الخاصة به.
- مكتبة المواد المعتمدة على Google Drive، ورفع ملفات PDF، ومزامنة الفهرس وإعادة فهرسة الملفات.
- مكتبة ملفات الامتحانات وآليات رفعها إلى Drive.
- التخزين الآمن لجلسات الدخول، والكاش دون اتصال، وإعدادات التطبيق.
- الإشعارات ودعم إرسالها، وصفحة التعلّم/الدراسة الشخصية.
- واجهات Eino الأحدث، وتسجيل الاستخدام، ومصفوفة مزودي الخدمة والـqueues.
- ترحيلات قاعدة البيانات الحالية وعقد الـAPI الخاص بالـMonorepo.

تغيير تسمية «الأنشطة» إلى «الفعاليات» وربطها بمورد `events` هو تغيير مقصود ومتوافق مع اتفاقات المشروع، وليس فرقًا تركناه دون معالجة.

## 5. التحقق الذي أُجري

- `npm --prefix services/api run check` — ناجح، وفحص صياغة ملفات JavaScript.
- `npm run build` — ناجح، وتم تجهيز بناء بوابة الموقع العامة.
- جميع فحوصات `ci/*.py` و`ci/*.mjs`: **40 من 40 ناجحة**، ومنها فحص عقد الإدارة، وCRUD، والمسارات، وسلامة مخطط قاعدة البيانات، وفحص الإصدار.
- فحص توازن الأقواس/المحددات في ملفات Dart المعدّلة: 14 ملفًا، ناجح.
- مخطط قاعدة البيانات: 35 ترحيلًا، 45 جدولًا، و170 فهرسًا حسب فحص المشروع.

**ما لم يُنفذ:** لم يمكن تشغيل `flutter analyze` أو اختبارات Flutter أو بناء APK/Desktop في بيئة التحرير، لأن Flutter/Dart SDK غير مثبتين هنا. لذلك نجاح فحوصات العقد وJavaScript لا يساوي إثبات نجاح ترجمة Flutter؛ ينبغي تشغيل `flutter analyze` والاختبارات والبناء في CI مزود بـFlutter قبل الإصدار.

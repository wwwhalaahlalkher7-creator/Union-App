# المرحلة 7 — مراقبة Eino الآمنة

تضيف هذه المرحلة مراقبة تشغيلية لـ Eino بدون تخزين محتوى المحادثات.

## ما يتم تسجيله

يتم تجميع الأحداث في فترات زمنية كل ساعة:

- `success` — إجابة ناجحة.
- `provider_error` — فشل من OmniRoute/المزود.
- `timeout` — انتهاء مهلة الطلب.
- `empty_response` — استجابة بدون محتوى صالح.
- `validation_invalid` — طلب غير صالح.
- `quota_window` / `quota_daily` / `quota_global` — رفض بسبب الحوكمة.
- `config_invalid` — إعداد نموذج Eino غير صالح.

يتم التفريق فقط بين `student` و`guest` و`unknown`.

لا يتم تخزين:

- prompt أو context أو response.
- عنوان IP.
- معرف الطالب.
- مفتاح OmniRoute أو بيانات المزود.

## واجهة الإدارة

للمستخدم الإداري ذي صلاحية `dashboard.read`:

```http
GET /api/v1/admin/security/eino-usage?hours=24
```

يمكن طلب من ساعة واحدة إلى 168 ساعة.

الاستجابة تعرض:

- حدود Eino الحالية.
- ملخصًا حسب نوع الحدث ونوع المستخدم.
- متوسط زمن الاستجابة للأحداث التي تحتوي على latency.
- العدادات الساعية.

## المبدأ

TRINEX يراقب صحة واستخدام بوابة Eino فقط. لا يحاول استبدال OmniRoute في اختيار المزود أو fallback أو حساب تكلفة المزود.

إذا فشلت قاعدة المراقبة نفسها، لا تفشل معها إجابة المستخدم؛ أخطاء telemetry تُسجل في Worker logs فقط.
